# Technical decisions

## Authentication

- `POST /api/auth/login` keeps the starter's `username` / `password` request. The challenge leaves the response and claims to the candidate. Success returns `{ token, expiresAt, user: { id, username, role } }`; `expiresAt` is UTC.
- Login reads the existing EF Core `User` and verifies its existing hash with `PasswordHasher<User>`. Wrong credentials and inactive accounts receive the same HTTP 401 message. Missing credentials receive HTTP 400.
- JWTs use HS256 and the existing configured issuer, audience, key, and expiration. Claims are `sub` (user ID), `unique_name` (username), and `role`. Validation requires a signed, unexpired token with the correct issuer, audience, and algorithm; clock skew is zero.
- Existing `Admin` and `Sales` roles may access products, customers, orders, and reports. The challenge specifies no distinction between these roles for those APIs. Login and health remain public.
- Auth integration tests use the actual ASP.NET Core pipeline and configured local `ChallengeDb`. The inactive-account test inserts a temporary user inside a shared SQL transaction and always rolls it back; seeded users are not changed. Run with `dotnet test backend/Challenge.slnx` after the local database setup.

## Products and customers

- `GET /api/products` returns `{ items, totalCount, page, pageSize }`. Each item contains `id`, `code`, `name`, `price`, `stockQuantity`, and `isActive`. The ID supports product selection when creating an order.
- Product search matches a substring of the code or name after trimming surrounding whitespace. Empty search means no search restriction. Matching follows SQL Server's configured collation. Products are active by default; `isActive=true` or `isActive=false` explicitly selects the corresponding status.
- Pagination defaults to page 1 and page size 10. Page must be positive, page size must be 1–100, and the offset must fit EF Core's integer `Skip` argument; invalid values return HTTP 400. Pages beyond the result set return empty items with the matching `totalCount`.
- EF Core applies status/search predicates, count, ordering by code then ID, and `Skip`/`Take` in SQL Server. DTO projections and `AsNoTracking` keep reads small. Count and page use separate queries; they are not a snapshot across concurrent catalog changes.
- `GET /api/customers` returns an array of active customers with only `{ id, code, name }`, ordered by code then ID for the order form. Customer pagination and CRUD are outside this step's requirements.
- Product/customer integration tests use the existing SQL transaction fixture, roll back temporary records, and inspect executed SELECT statements to verify database-side filtering and pagination. JWT rules are unchanged.

## Order creation

- `POST /api/orders` accepts `{ customerId, items: [{ productId, quantity }] }`. IDs and quantities must be positive; items must be nonempty and nonnull. Duplicate product IDs are rejected with HTTP 400. Unknown JSON fields, including client prices, totals, status, order number, dates, and creator, are rejected with HTTP 400.
- Success is HTTP 201 with `Location: /api/orders/{id}` and `{ id, orderNumber, customerId, orderDate, status, totalAmount, createdBy, items: [{ productId, quantity, unitPrice, totalPrice }] }`. Status is `Confirmed`, timestamps are UTC, and the creator is an existing active user identified by JWT `sub`.
- Missing customer/product returns HTTP 404; inactive customer/product returns 400; unavailable or insufficient stock returns 409. Business errors use ProblemDetails with a stable `code` and useful `title`. Malformed/model-invalid input uses ASP.NET Core validation ProblemDetails. Existing JWT 401/403 and generic unexpected-error handling are preserved.
- A SQL Server transaction at ReadCommitted covers all stock updates and insertion of the order/items. Products are processed in ascending ID order. `ExecuteUpdateAsync` subtracts from the database value only when the product is active and stock is sufficient; exactly one affected row is required. Products are never tracked, so `SaveChangesAsync` cannot overwrite the atomic stock updates.
- Price is read after the successful stock update, while the SQL write lock is held, and copied to `OrderItem.UnitPrice`. Line/order totals use decimal arithmetic and must fit the existing decimal(18,2) columns. The transaction commits only after all rows are saved. Early returns, exceptions, and cancellation dispose the uncommitted transaction and roll back every change.
- Order numbers are 32-character GUIDs protected by the existing unique index. No schema changes or retry mechanisms are required. The Location URL names the existing detail route, implemented in Step 5.
- Order integration tests use fresh SQL connections per request. A test-only asynchronous gate waits until two stock UPDATE commands have arrived on different physical connections, then releases them together. It provides test synchronization, not production inventory locking. The required LAPTOP-001 race uses quantities 4 and 3 with initial stock 5.
- Tests create identifiable temporary customers/products and remove only their own orders/items and records afterward. The laptop's previous stock and UpdatedAt are restored in the same cleanup transaction. The order-test collection runs separately from other test collections so committed fixtures cannot affect their catalog counts; the two HTTP requests inside each concurrency test still execute together. Existing users and unrelated databases are never changed. Another test injects failure after SQL has saved the order/items to verify rollback before commit.

## Order queries

- `GET /api/orders` accepts optional `orderNumber`, `customerId`, `status`, `fromDate`, `toDate`, `sortBy`, `sortDirection`, `page`, and `pageSize` query parameters. No request body is needed. The challenge leaves exact sorting options, defaults, date boundaries, and response shape unspecified; these decisions follow the existing Angular filter names and catalog pagination contract.
- Order-number search matches a substring after trimming; blank search imposes no restriction. Matching uses the existing SQL Server collation. Customer ID must be positive; a nonexistent customer simply matches no orders. Status accepts the existing `Confirmed`/`Cancelled` enum names or their defined numeric values 1/2. Malformed or undefined values return HTTP 400 validation ProblemDetails. Historical orders remain visible when their customer or products are now inactive.
- `fromDate` and `toDate` are date-only query values, conventionally `yyyy-MM-dd`. Both boundaries include the entire UTC calendar day: `OrderDate >= fromDate` and `OrderDate < toDate + 1 day`. Either boundary may be omitted. An invalid date or reversed range returns HTTP 400. `9999-12-31` includes the maximum SQL datetime2 day without attempting an overflowing next-day calculation. The existing UTC order-date convention is restored on output because datetime2 does not retain `DateTime.Kind`.
- `sortBy` supports `orderDate` (default), `orderNumber`, or `totalAmount`; `sortDirection` supports `asc` or `desc` (default). Sort options are trimmed and case-insensitive. Every ordering adds the unique order ID in the same direction as a tie-breaker. Invalid options return HTTP 400. Defaults are newest orders first, page 1, page size 10. The existing limits apply: positive page, page size 1–100, and offset within the integer `Skip` range. A page beyond the result set returns empty items with the matching total count.
- The list response is `{ items: [{ id, orderNumber, customerId, customerName, orderDate, status, totalAmount }], totalCount, page, pageSize }`. Status is a string and dates are UTC. `AsNoTracking` DTO projection avoids loading items or user data. Filtering, ordering, count, offset, and limit run in SQL Server. Count and page are two queries rather than a shared snapshot; concurrent writes can change the result between them, and between separate page requests.
- `GET /api/orders/{id}` returns `{ id, orderNumber, customerId, orderDate, status, totalAmount, createdBy, customer: { id, code, name }, createdByUser: { id, username }, items: [{ productId, quantity, unitPrice, totalPrice, productCode, productName }] }`. The small customer DTO is reused and detailed items extend the existing item DTO. Creator identity contains only its ID and username. Positive missing IDs return HTTP 404 ProblemDetails with `code: order_not_found`; nonpositive integer IDs return HTTP 400 with `code: invalid_order_id`. Values outside the existing integer route constraint return HTTP 404.
- Details use one read-only SQL projection joining customer, creator, and product descriptions; items are ordered by product ID then item ID. Amounts come directly from saved `OrderItem.UnitPrice`, `OrderItem.TotalPrice`, and `Order.TotalAmount`, without querying current product prices or recalculating totals. Product/customer names and codes reflect current descriptions, since the existing schema snapshots only prices. No password hashes, stock, timestamps unrelated to the response, or EF navigation objects are exposed.
- Both query endpoints preserve the existing Admin/Sales authorization. Order creation, inventory transactions, schema, migrations, seed logic, Docker, and Angular are unchanged. Query tests use the existing SQL Server fixture and nonparallel order collection, insert only their own temporary records inside a shared transaction, roll it back, and assert that those records are gone after each test. Tests inspect executed SQL and change only temporary product prices to prove historical amounts remain stable. All previous creation/concurrency tests are retained unchanged.

## Top products report

- `GET /api/reports/top-products` has no request body and returns the challenge's array contract: `[{ productCode, productName, quantitySold, totalSales }]`. No extra report parameters, row limits, or pagination are added. `quantitySold` is a JSON integer backed by `long`; `totalSales` is a decimal JSON number. Both existing Admin/Sales roles may read the report; missing authentication returns 401 and a token without either permitted role returns 403.
- The challenge does not specify reporting statuses, mandatory date bounds, or boundary semantics. Only `Confirmed` orders contribute to sales; `Cancelled` orders do not. Current customer/product active status and stock do not filter historical sales. Product codes/names reflect the existing product records, while monetary amounts remain historical.
- Optional `fromDate` and `toDate` use the order-list convention: date-only values (`yyyy-MM-dd`) and inclusive UTC calendar days. A missing bound imposes no restriction on that side; omitting both reports all confirmed sales. SQL uses `OrderDate >= fromDate` and `OrderDate < toDate + 1 day`. The maximum date `9999-12-31` is handled without an overflowing next-day calculation. Malformed dates and reversed ranges return HTTP 400 validation ProblemDetails before querying sales. No matches return HTTP 200 with `[]`.
- One `AsNoTracking` EF Core query filters order items through their parent orders, groups by product ID/code/name, sums quantities and saved `OrderItem.TotalPrice`, and sorts in SQL Server before materialization. Quantities are cast to SQL bigint before `SUM` so cumulative sales can exceed one item's int range. Amounts never use current `Product.Price`, a recomputed unit-price multiplication, or the order header's total. Results sort by quantity descending, then product code ascending, then product ID ascending for deterministic ties.
- Thirty SQL Server integration cases cover the exact response, shared-product aggregation at different historical prices, date boundaries and optional bounds, invalid/empty ranges, cancelled orders, inactive historical records, price changes, stored totals, quantity overflow, ordering, and permissions. The SQL test records its executed statement and verifies `WHERE`, `GROUP BY`, bigint/decimal `SUM`, and `ORDER BY` in a single query. The existing transaction fixture and order collection isolate temporary R6 records; every case rolls back and verifies cleanup. All 171 previous tests and all order/inventory code remain unchanged.

## Angular integration

- The five existing Angular 19 standalone pages, router, ReactiveForms login, template-driven page forms, HttpClient, guard, and interceptor are retained. Small typed API/auth services and one error formatter connect the existing contracts; no libraries, architectural layers, report page, or backend changes are added. The existing `environment.apiUrl` matches the backend's `http://localhost:5089`; the browser verifies CORS from `http://localhost:4200`.
- Authentication stores only `{ token, expiresAt, user }` in tab-scoped `sessionStorage`, restoring it on reload; credentials are never persisted. Expiry uses the earlier of the response timestamp and JWT `exp`, with a timer for logout and checks before routing/requests. Reading `exp` schedules expiry; signature/issuer/audience authorization remains the backend's responsibility. Malformed/expired sessions are cleared, login redirects to products, and logout redirects to login. No refresh or additional authentication flows are introduced.
- The guard protects all existing business routes. The interceptor attaches Bearer tokens only to the configured `/api/` URL, excluding login. Protected API 401 clears the session and redirects; login 401 stays on the form with its error, and 403 displays a permission error. A late 401 from an earlier token cannot clear a newer session.
- Products and orders use server pagination at 10 rows, with search/filter changes resetting to page 1. Product status selects active/inactive records. Orders send the documented number/customer/status/date/sort parameters. Date inputs are sent as date-only strings without local-time conversion; displayed order dates are labeled UTC. Loading, empty results, network failures, validation ProblemDetails, and business messages are shown in the existing pages.
- The order form loads active customers and searches/pages active products, retaining selected products when the catalog page changes. It validates selected customer, nonempty/distinct products, and positive integer quantities, supports item removal, and blocks edits/duplicate submissions while pending. Its totals are JavaScript-number estimates for convenience; the server's saved amounts are authoritative. POST explicitly contains only `customerId` and item `productId`/`quantity`. HTTP 409 gives a clear stock message without an automatic retry; success navigates using the returned order ID to the detail route named by Location.
- Order details load from the route ID, handle invalid IDs/404 and ID changes, and display the saved unit prices, line totals, order total, customer, and creator. They never fetch current product prices or recalculate saved amounts.
- The final audit reran all 38 frontend tests using Karma/Jasmine in ChromeHeadless and all 201 SQL Server backend tests, with zero failures/skips. Separate real Chrome-to-API verification passed 31 checks, including all five screens, both seed users, guard/JWT/CORS, product and order pagination, date/status/customer/search/sort filters, creation, 409/401/404, logout/expiry, and historical detail/report amounts after an owned product's price changed. Its temporary customer, 12 products, and 12 successful orders/items were removed; the preexisting user order and original database counts/stock were preserved. No package or Docker changes were needed.

## Final audit limits

- The stock-5, quantities-4-and-3 test used two real SQL connections: A returned 409, B returned 201, final stock was 2, and exactly one order/item persisted. Cleanup restored the prior laptop stock and timestamp. The executed statement checks verify filtering/pagination and report grouping/sums in SQL; the original migration remains `20260831073412_InitialCreate`.
- Restore/build and documented startup commands succeeded. NU1510 remains a nonblocking warning for the starter's redundant package reference. The audit ran with .NET SDK 10.0.401, Angular 19.2.25, and Node 24.20.0; Node 22.x is documented for the [Angular 19 compatibility range](https://angular.dev/reference/versions). A separate Node 22 run was not performed.
- This supplied directory has no `.git` history, so a complete historical diff against the untouched starter cannot be established here. Current-stage source hashes verify that application code, tests, entities, migrations, seed logic, lockfiles, and Compose were unchanged. Historical compliance with the three-hour time limit was not measured. Temporary audit scripts/browser profiles were removed; generated results/build folders are excluded from submission source.
