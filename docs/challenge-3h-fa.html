چالش ۳ساعته توسعه‌دهنده ارشد فول‌استک

سیستم کوچک فروش و موجودی با ASP.NET Core، Angular و SQL Server. هدف، حجم کد نیست؛ صحت، سازگاری دیتابیس، امنیت و قضاوت مهندسی است.

۱. هدف

یک جریان فروش و موجودی را کامل کنید: ورود، مشاهده محصول، ایجاد سفارش، لیست و جزئیات سفارش، و گزارش پرفروش‌ها.

ارزیابی روی این محورهاست: مهندسی بک‌اند، طراحی دیتابیس، EF Core / SQL، طراحی API، منطق کسب‌وکار، تراکنش، همزمانی، امنیت، مبانی Angular، تست، تصمیم فنی، و مدیریت محدوده.

شما قرار نیست هر قابلیت ممکن را بسازید. اولویت با صحت، امنیت، منطق کسب‌وکار، همزمانی، سازگاری دیتابیس و کیفیت کد است.

۲. پشته فناوری — الزامی

  • ASP.NET Core Web API
  • Entity Framework Core
  • SQL Server
  • Angular
  • TypeScript
  • JWT Authentication

۳. استارتر چه دارد و چه چیزی با شماست

معمولاً در استارتر آماده است

  • پروژه API قابل build و GET /api/health
  • Swagger در محیط Development
  • مدل‌های دامنه: User، Product، Customer، Order، OrderItem
  • Migration اولیه و Seed (کاربران، حدود ۱۰ محصول، حدود ۵ مشتری)
  • زیرساخت JWT (پیکربندی اعتبارسنجی توکن) — صدور توکن با شماست
  • زیرساخت خطای متمرکز، بدون تعریف همه کدهای خطای کسب‌وکار
  • اپ Angular با روت‌های پایه و اسکلت صفحات
  • پروژه تست آماده، بدون تست‌های کامل شما
  • Docker Compose فقط برای SQL Server

شما باید پیاده کنید

  • ورود کامل و صدور JWT
  • API محصول، سفارش و گزارش طبق بخش API
  • DTOها، اعتبارسنجی بک‌اند، و رفتار خطا
  • ایجاد سفارش به‌همراه به‌روزرسانی موجودی، به‌صورت سازگار
  • رفتار صحیح وقتی دو سفارش تقریباً همزمان به یک موجودی محدود می‌رسند
  • اتصال Angular به API، توکن، محافظت روت، و صفحات کاربردی
  • تست‌های معنادار روی منطق حیاتی
  • یادداشت کوتاه تصمیم‌های فنی (مثلاً NOTES.md)
استارتر راه‌حل سفارش، تراکنش، همزمانی و اعتبارسنجی کسب‌وکار را به شما نمی‌دهد. آن تصمیم‌ها بخش اصلی ارزیابی است.

۴. راه‌اندازی

  1. SQL Server را با Docker بالا بیاورید: docker compose up -d
  2. مایگریشن را اعمال کنید (یا طبق README استارتر؛ API ممکن است هنگام استارت مایگریشن را اعمال کند): 
    dotnet ef database update --project backend/src/Challenge.Api --startup-project backend/src/Challenge.Api
  3. بک‌اند: dotnet run --project backend/src/Challenge.Api
  4. فرانت‌اند: cd frontend/challenge-app && npm start

آدرس‌های معمول توسعه: API روی پورت اعلام‌شده در README استارتر (نمونه: http://localhost:5089)، Swagger در /swagger، Angular روی http://localhost:4200.

اگر Docker برای SQL در محیط شما مشکل ساخت، روش جایگزین را از README استارتر دنبال کنید. Docker کردن کل API و Angular الزامی نیست و نباید وقت ۳ ساعته را بگیرد.

۵. مدل داده (حداقل)

User

Id، Username، PasswordHash، Role (Admin / Sales)، IsActive، CreatedAt

Product

Id، Code (یکتا)، Name، Price (نامنفی)، StockQuantity (نامنفی)، IsActive، CreatedAt، UpdatedAt

Customer

Id، Code (یکتا)، Name، PhoneNumber، IsActive، CreatedAt، UpdatedAt

Order

Id، OrderNumber (یکتا)، CustomerId، OrderDate، Status (Confirmed / Cancelled)، TotalAmount، CreatedBy، CreatedAt، UpdatedAt

OrderItem

Id، OrderId، ProductId، Quantity، UnitPrice، TotalPrice

UnitPrice باید قیمت لحظه ایجاد سفارش باشد، نه قیمت جاری محصول در آینده.

۷. API مورد انتظار

مسیر دقیق را می‌توانید کمی تنظیم کنید، اما قابلیت معادل الزامی است. شکل DTO درخواست/پاسخ با شماست؛ پیاده‌سازی نهایی DTO در استارتر داده نمی‌شود.

متدمسیر نمونهشرح
POST/api/auth/loginورود با نام کاربری و رمز. claims، انقضا، شکل پاسخ، بررسی رمز و خطا با شما
GET/api/productsجستجو، محصولات فعال، صفحه‌بندی. CRUD محصول لازم نیست
GET/api/customersدر صورت نیاز صفحه ایجاد سفارش (حداقل لیست قابل انتخاب)
POST/api/ordersایجاد سفارش و کاهش موجودی
GET/api/ordersجستجوی شماره سفارش، فیلتر مشتری/وضعیت/تاریخ، مرتب‌سازی و صفحه‌بندی در دیتابیس
GET/api/orders/{id}جزئیات با قیمت تاریخی آیتم‌ها
GET/api/reports/top-productsپرفروش‌ها با fromDate و toDate؛ تجمیع در SQL نه در حافظه اپ

نمونه خروجی گزارش:

[
  {
    "productCode": "LAPTOP-001",
    "productName": "Laptop",
    "quantitySold": 125,
    "totalSales": 6250000000
  }
]

لیست سفارش و محصول را کامل در حافظه برنامه بار نکنید. فیلتر و صفحه‌بندی باید در سطح دیتابیس باشد.

۹. اعتبارسنجی کسب‌وکار — بک‌اند

  • مشتری وجود داشته باشد و فعال باشد
  • محصول وجود داشته باشد و فعال باشد
  • تعداد بزرگ‌تر از صفر باشد
  • سفارش حداقل یک آیتم داشته باشد
  • موجودی کافی باشد
  • کاربر احراز هویت شده باشد و مجوز داشته باشد
فقط اعتبارسنجی فرانت‌اند قابل قبول نیست.

۱۰. قیمت تاریخی

هنگام ایجاد سفارش، قیمت محصول باید روی OrderItem.UnitPrice ذخیره شود. اگر بعداً Product.Price عوض شود، سفارش‌های قبلی نباید تغییر کنند. محل این منطق با شماست.

۱۱. تراکنش

ایجاد سفارش چند عملیات است: ایجاد Order، ایجاد آیتم‌ها، به‌روزرسانی موجودی. اگر یکی شکست بخورد، دیتابیس نباید سفارش ناقص داشته باشد.

مرز تراکنش، رفتار شکست، و برگشت تغییرات را خودتان تعیین کنید. راه‌حل از پیش در سند یا استارتر نیست.

۱۲. همزمانی — مهم‌ترین بخش

در Seed حداقل این محصول وجود دارد:

Product Code = LAPTOP-001
StockQuantity = 5

دو درخواست تقریباً همزمان:

درخواست A: تعداد 4
درخواست B: تعداد 3

سیستم باید تضمین کند:

  • هر دو سفارش نمی‌توانند موفق شوند
  • موجودی هرگز منفی نشود
  • وضعیت دیتابیس سازگار بماند
  • سفارش ناموفق پاسخ HTTP مناسب بدهد
  • سفارش موفق موجودی را درست کم کند
استراتژی را خودتان انتخاب و در NOTES توضیح دهید. این سند عمداً روش پیاده‌سازی را دیکته نمی‌کند. ارزیاب بعداً از شما می‌پرسد اگر دو درخواست دقیقاً هم‌زمان برسند چه می‌شود.

۱۳. خطا

زیرساخت خطای متمرکز در استارتر هست. کدهای خطای کسب‌وکار را خودتان طراحی کنید. موقعیت‌هایی که باید پوشش دهید:

  • اعتبار ورود نامعتبر
  • عدم احراز هویت / عدم مجوز
  • محصول یا مشتری پیدا نشد
  • موجودی ناکافی
  • تعارض در به‌روزرسانی همزمان
  • سفارش نامعتبر

Exception خام و stack trace را به کلاینت ندهید. Angular باید پیام مفید نشان دهد.

۱۴. امنیت

  • هش رمز عبور
  • اعتبارسنجی JWT
  • مجوزدهی سمت سرور (نه فقط در Angular)
  • اعتبارسنجی ورودی
  • عدم افشای اطلاعات حساس
  • جلوگیری از SQL Injection و overposting
  • status code مناسب

راز واقعی production را hard-code نکنید. از تنظیمات توسعه / متغیر محیطی استفاده کنید.

۱۵. تست

پروژه تست آماده است. تست‌های معنادار برای منطق حیاتی بنویسید. حداقل این سناریوها را در نظر بگیرید:

  • سفارش معتبر
  • تعداد نامعتبر
  • موجودی ناکافی
  • محصول غیرفعال
  • مشتری نامعتبر
  • سفارش همزمان روی موجودی محدود
  • مجوزدهی

درصد پوشش دلخواه ملاک نیست.

۱۶. Docker

هدف استارتر این است که SQL Server سریع بالا بیاید. کل اپ را Docker کردن اختیاری است و جزء امتیاز اصلی نیست. سقف ۳ ساعت مهم‌تر از کامل بودن Docker است.

۱۷. محدودیت‌ها و مدیریت محدوده

  • CRUD کامل محصول لازم نیست
  • زمان را صرف طراحی بصری پیشرفته نکنید
  • معماری پیچیده (میکروسرویس، پیام‌رسان، چند دیتابیس و مشابه) بدون دلیل قوی اضافه نکنید
  • اگر وقت کم شد، ظاهر و قابلیت فرعی را کم کنید؛ هسته سفارش و موجودی را قربانی نکنید

تصمیم‌های مهم فنی را کوتاه مستند کنید.

۱۸. چک‌لیست قبل از تحویل

  1. ورود کار می‌کند
  2. محصولات با جستجو/صفحه‌بندی از API می‌آیند
  3. ایجاد سفارش موجودی را کم می‌کند
  4. موجودی ناکافی رد می‌شود
  5. دو سفارش همزمان روی LAPTOP-001 بیش از موجودی مصرف نمی‌کنند
  6. لیست سفارش در دیتابیس فیلتر/صفحه‌بندی می‌شود
  7. گزارش تجمیع SQL دارد
  8. قیمت تاریخی حفظ می‌شود
  9. تست حیاتی نوشته شده
  10. NOTES کوتاه است
